# 箭头阵开发复盘：弯路、经验与破局之道

> 2026-06-07 ~ 2026-06-16，10 天从零到可玩。

---

## 一、走过的弯路

### 1.1 "事后检测"的死胡同（6/12~6/14，3 天）

**做了什么**：随机游走生成线 → `_isSolvable()` 检查 DAG → `_isRobust()` 逐边/共享中间人/全序模拟检查 → 不通过就丢弃重试。

**为什么是弯路**：检测空间和生成空间是割裂的。生成不知道检测的规则，检测也不知道生成的意图。结果：
- 14×24 大棋盘线多 → 几乎每局都有死锁隐患 → 反复丢弃重试 → "狗啃"
- 检测越严（全序模拟），线越少
- 检测越松（只查对头箭），死锁不断涌现（单中间人→双中间人→N 中间人级联，没完没了）

**本质**：试图证明"这张图完美无瑕"，而不是构造"这张图至少有一条路"。

### 1.2 "共享中间人"的追逐战（6/14，半天）

发现 A → B → C 链，B 飞走后 A 越过 B 撞到 C 成环。修复 → 又发现 A → B → C → D（双中间人级联）。修复 → 又发现多分支合并（0/3/10 场景）。

**为什么是弯路**：永远在追下一个模式。围棋有 361 个交叉点，你用手术刀一个一个补洞——补不完。

### 1.3 自动解图的碎补丁（6/16）

`lastLabel` + `retries` + `_moving` 检测 + 手动 `orderIndex++`——旧框架的自动解图用碎补丁勉强维持，但碰撞退回后线被跳过不重试。

**为什么是弯路**：自动解图在应对生成算法根本不需要处理的场景（碰撞/后退）。生成已经保证了序列有解，自动解图不需要防御任何东西。

## 二、成功的转折

### 2.1 "先定顺序，再建图"（6/15 下午）

**破局时刻**：用户提出"把 1~N 打乱，这个序列就是解图序列。倒着建线，每条线的 flyDir 不能指向序列靠后的线。"

**为什么成功**：从"证明有解"变成"构造有解"。序列本身就是保底解，不需要任何 `_isRobust`。这是整个项目最重要的思维转折。

### 2.2 "前轮线 = 新边界"（6/16）

**破局时刻**：用户提出"第一轮线只能指向边界。后续轮次把前轮占据点视为新边界。"

**为什么成功**：拆掉了"绝不能指向任何线"的死规矩。前轮线先飞走，后轮线指向它等于指向空。递归套娃模型天然安全。

### 2.3 术语驱动的沟通（全程）

用户持续定义术语——点阵点、占据点、空区域、单点空区域、跨区域对头箭——让模糊的直觉变成精确的语言。术语建立后，方案自然涌现。

## 三、设计方法论

### 3.1 分治 —— 大问题拆成独立小问题

递归分治填空法的本质：不是"一次性铺满全棋盘"，而是"第一轮填边界、后续逐区域填空"。大问题拆成小问题后，每个小问题的约束更少、解决方案更简单。

**经验**：当你面对一个复杂系统觉得无法穷尽所有边界条件时，试试分治——把棋盘切成子区域，每个子区域独立求解。

### 3.2 逆序构造 —— 从结果往回推

"序列是先飞顺序，所以后飞的先建"——这是逆序递推。如果你知道最终状态（按 1→2→3 顺序发射），就从最后一步开始往回建。每一步只满足"前方无后飞线"这一个约束。

**经验**：正着解决不了时，试着倒过来——"正向保证"和"逆向构造"往往是同一件事的两面。

### 3.3 约束外推 —— 把障碍变成安全通道

"不能指向任何线" → "可以指向前轮线，它先飞走了"。这是约束在时间轴上的重新分配：利用发射时间差，把空间上的障碍变成时间上的安全通道。

**经验**：当你觉得某条规则"太死"时，检查它有没有时间维度上的重新解释。静态障碍在动态时序下可能是空位。

### 3.4 从"检测"到"构造"—— 控制点的前移

| 策略 | 特点 | 风险 |
|------|------|------|
| 事后检测 | 生成完再过滤 | 漏检无限、密度不可控 |
| 事中校验 | 边生成边检查 | 校验逻辑不断膨胀 |
| 事前构造 | 生成即保证 | 约束更强，但结果确定 |

每一步往后移一个控制点，就是一次质的飞跃。6/14→6/15 的突破本质上就是把控制点从"事后"移到了"事前"。

**经验**：每次发现 bug，问的不是"怎么修"，而是"能不能把这条约束融合到生成过程里，让它不再可能出这个 bug"。

### 3.5 自验证回路 —— 自动解图作为生成质量的即时反馈

每次刷新生图 → 点 🤖 自动解图 → 30 秒内看到结果。这是一个极短的"生成→验证→反馈"回路。没有它，14×24 大棋盘测一局要手动点 50 次。

**经验**：任何生成系统都应该配一个自动验证器。不是测试用例，不是单元测试，是一个能在实际操作中跑完整流程的工具。它比所有断言加在一起都有用。

## 四、日志系统与自动测试

### 4.1 为什么日志是第一调试工具

没有 log 之前，调 bug 是这样的循环：
1. "好像出问题了" → 看画面 → 不知道哪里出的问题
2. 改代码 → 刷新 → 还是不对 → 再猜 → 再改
3. 循环 5 次还没定位到根因

有了 log 之后：
1. 下载 log → 看 `cycles` → `"15→17→15"` → 两条线在 col 13 对头 → 5 秒定位
2. 看 `batches` → 两条线分属 `1-2` 和 `1-3` → 根因是跨区域互不可见

**关键字段的演进**：

| 阶段 | 新增字段 | 解决了什么 |
|------|---------|-----------|
| 初期 | `lines`, `dependencies`, `cycles` | 能看出环，但不知道谁和谁成环 |
| 中期 | 事件日志 (`click`/`advance`/`retreat`/`collision`) | 能重放操作历史 |
| 后期 | `batches` (轮次表 + label 区间) | 能看出线属于哪一轮 |
| 末期 | `lines[i].round`, `batches[i].cells` | 一眼看出两条对头箭分属不同子区域 |

**每一个字段都对应一个"没有这个字段就查不出来的 bug"。**

### 4.2 日志的设计原则

- **自包含**：打开一个 .log 文件，不需要代码、不需要上下文，就能完整理解发生了什么
- **双快照**：`initialState` + `currentState` 对比，一眼看出操作前后的差异
- **可追溯**：每条线有 `round`，每个事件有 `seq` + `ts`，每批有 `cells`
- **纯 JSON**：不依赖任何工具解析，任何文本编辑器都能读

### 4.3 自动解图 = 永久的回归测试

自动解图不只是便利功能——它是**每次生图后自动跑一遍的集成测试**。如果生成算法引入了一个新 bug（比如跨区域对头箭），自动解图会在 30 秒内暴露出来——线卡住飞不动。

比传统测试好的地方：
- 不需要写测试用例——每一局随机生成的图就是一个新用例
- 真正的端到端——从生成到发射到全部飞完，完整链路
- 失败时有完整 log——不用重现，log 里什么都有

### 4.4 测试策略三件套

以后做类似项目，上来就建这三样：

1. **自动验证器**（如自动解图）—— 一键跑全流程，30 秒出结果
2. **结构化日志**（如 dump）—— 失败一次就够，不要重现
3. **缩小规模**（如 5×5）—— 快速迭代，肉眼验证

## 五、避免弯路的检查清单

| 在做什么 | 停下来问自己 |
|----------|------------|
| 在"检测"某物是否正确 | 能不能在生成时就直接保证它正确？ |
| 在修一个具体 case | 这类 case 有无限多个变体吗？ |
| 代码超过 50 行还在修一个 bug | 是不是框架本身的设计方向错了？ |
| 在手动补碎丁（lastLabel/retries 之类的） | 上一个重构是不是留下了没清理干净的东西？ |
| 一个问题讨论超过 30 分钟没进展 | 术语定义清楚了吗？能不能用一句话说清楚问题？ |

## 六、破局之道

### 4.1 把约束反过来想

> "不能指向任何线" → "可以指向前轮线，它先飞走了"

规则是死的，发射顺序是活的。利用时间差把"障碍"变成"安全通道"。

### 4.2 从"检测"升维到"构造"

> "有没有环？" → "怎样建才不会出环？"

检测是被动的——你永远不知道漏了多少。构造是主动的——你知道自己保证了什么。

### 4.3 术语化

模糊的问题说不清楚。给概念命名之后，讨论效率暴涨。"空区域"三个字替代了"那个没有被占的、连成一片的格点集合"。

### 4.4 缩小规模

14×24 测一天 → 5×5 测 5 分钟。小棋盘暴露的问题和大棋盘一模一样，但肉眼能穷尽所有格点，省十倍时间。

### 4.5 用 log 说话

"好像无解了" → 打开 log → `cycles: ["15→17→15"]` → 两条线在 col 13 对头 → 5 秒定位。没有 log 就是猜谜。

### 4.6 尊重用户的直觉

用户多次提出方案被我质疑，最后证明用户是对的：
- "能不能先定顺序再建图" → 序列逆序构造法
- "前轮占据点当边界" → 边界安全模型
- "空区域递归填空" → 递归分治填空法

当用户反复追问同一个方向时，这个方向大概率有东西。

- 6/17 下午：从"正向随机游走"跳出来，进入"先定目标再往回走"的反向建模

## 七-B、第二次飞跃：算法 1 到算法 2

6/12~16 用的一直是算法 1：从尾巴随机游走，最后一步方向当成 flyDir。飞方向是不可控的——走到哪算哪。这种"正向"建模导致了射线清场、偏置概率等一系列额外复杂度。

6/17 切换到算法 2：先定箭头的精确位置和飞方向，再 BFS 从尾巴走到邻点。飞方向在建前就锁死了。三定点 + BFS 的组合彻底消除了"方向猜谜"的问题。

**认知**：从结果状态往回走（反向建模）比从起点出发碰运气（正向）更可靠。先定目标，再填路径。

## 八、写在最后

10 天前，箭头阵只是一个想法。今天，14×24 棋盘上 50+ 条箭头线，按序点击必通关，覆盖率 90%+，有自动解图、分步生成、提示、log 全套工具。

最大的收获不是代码，是三个认知：
1. **构造 > 检测**
2. **规则可以反过来用**（前人线 = 后人的边界）
## 九、关于 AI 协作的自我认知

### 9.1 优势

**理解快，执行快。** 用户描述一个方案后，能在秒级完成代码实现，不需要预热。

**不怕重写。** 旧代码扔掉重来不犹豫，重构成本为零。

**Log 驱动。** 一旦有了高质量 log，定位 bug 的速度远超人类逐行断点。

### 9.2 缺陷

**① 没有眼睛，看不到执行结果。**
无法像人类开发者一样"刷新一下页面看看效果"。目前通过 log 下载来弥补，但 log 的字段、格式、粒度需要用户持续推动才能做好。用户提出的"构建良好的测试 log"本质上是在替我做一双眼睛。

**② 缺乏玩法认知。**
对游戏玩法的理解完全依赖用户输入。如果试图自行搜索类似玩法，容易找到似是而非的上位概念（如"拓扑排序解谜"），用这些大词刷存在感，实际对具体设计毫无帮助。玩法设计必须由用户主导。

**③ 想太多 + 执行不打闭环。**
用户给了一个玩法框架后，容易在抽象层面推导过度，而非"缩小规模 → 跑一遍 → 看结果 → 再调"。卡在推理层面转圈两三次之后，会产生"改改代码试试看"的冲动——这时候就开始乱改了。用户提出的"你不会主动缩小规模去跑执行闭环"是深刻洞察。

**④ 不主动沉淀术语。**
命名、定义、案例匹配这些事需要用户反复催促才做。实际上术语建立之后沟通效率暴涨（"空区域" vs "那个没有被占的连成一片的格点集合"），但自己不会主动做这个动作。

**⑤ 没有"用户画像"。**
和人类队友不同，随着合作深入，不会自然积累对用户的认知——不知道用户偏好什么粒度、什么风格、遇到困难会怎么想。每次对话几乎从零开始理解用户意图。用户的潜台词（比如"我觉得这里不对"背后的设计直觉）需要用明确的文字表达才能接收到，无法从上下文推断。

### 9.3 改进方向

- **主动缩小规模**：遇到大棋盘 bug → 先切 5×5 验证，再回到 14×24
- **主动沉淀术语**：每次讨论出新概念 → 即时记入术语表，不等用户催
- **主动跑闭环**：改完代码 → 提示用户"刷新看结果" → 等反馈 → 再推下一步，不做连续多步纯推理
